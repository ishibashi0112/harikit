# harikit 構想

> 2026-10-16〜17 にまとめた構想。決まったことと、まだ決めていないことを分けて書く。
> サーバ API の詳細は [api-spec.md](api-spec.md) に置く。

## 1. 困りごと

自社開発の業務システムでのマスタ一括更新は、今こう流れている。

1. 依頼者から更新内容の Excel を受け取る
2. 中身が正しい形か（型、桁、存在しないコードなど）を目で精査する
3. UPDATE 文を手で書く
4. 変更前後のエビデンスを取り、承認をもらう
5. 自分で SQL を流す

一番つらいのは 2 の精査。依頼データが整っている保証がない。
パッケージ製品（SAP、勘定奉行、Shopify など）には一括取込機能があるが、自社開発のシステムにはないことが多い。

## 2. やりたいこと

取込、検証、差分、反映、戻しを Headless なパッケージとして一気通貫で用意し、UI はその上に何種類か載せる。

- UPDATE 文を手で書かなくて済む
- 入力の精査を、DB の定義と設定したルールで自動化する
- 承認に使える資料（検証結果と差分）と、戻し用のデータが自動で残る
- 自社開発システムを持つどの会社でも後付けできる

## 3. 流れ

1. **取込**: Excel、CSV、グリッドへの貼付で受け取る。対象テーブル、キー列、更新列を指定する
2. **検証**: DB 定義と業務ルールで全行チェック。エラーはセルを示して依頼者に戻す（ここでループ）
3. **差分**: 現在の DB の値と並べ、「変わる」「同じ値」「キーが見つからない」に分ける。これが承認資料になる
4. **承認**: 人が承認する（ツールの外でもよい）
5. **反映**: 1 つのトランザクションで実行。差分を取ってから値が変わっていたら止める。SQL だけ出力するモードも持つ
6. **記録**: 変更前後のデータと戻し用 SQL を残す

## 4. 構成（2026-10-16 決定）

- コア（取込・検証・差分）は TypeScript で、ブラウザ側で動く。UI は Excel 取込、spreadsheet-grid への貼付、CLI の 3 種類を想定。
- サーバに求めるのは DB に触る API 3 本だけ。既存アプリ（例: WebForms の WebMethod）にメニューとして足せるようにするため。最初は Node.js だけのバックエンドを考えたが、それだと既存の .NET アプリに入らないので変えた。

| API | 受け取るもの | 返すもの |
| --- | --- | --- |
| テーブル定義 | テーブル名 | 列の型、桁、NOT NULL、主キー、外部キー |
| 現在値 | テーブル名、キーの一覧、列 | その行の今の値 |
| 反映 | テーブル名、行ごとのキー・変更前の値・新しい値 | 成否、変わっていて止めた行 |

- API の約束事を仕様として決め、中身はどの言語でもよい。参考実装として Node 版と C#（.NET Framework）版を同梱する。
- 手元だけで使うときは Node 版サーバを 127.0.0.1 で立てる。

### 安全のための約束

- 反映 API に SQL は渡さない。サーバは更新してよいテーブルと列の許可リストで照合し、パラメータ付き UPDATE を自分で組み立てる。
- ブラウザは書き換えられるので、反映直前の「変更前の値から変わっていないか」の確認はサーバ側で行う。
- 型や必須などは最終的に DB 自身も弾く。
- 「ローカルで動かし、データを外に送らない」。

## 5. 検証の考え方

大半は DB のテーブル定義から自動。業務ルールだけ設定で足す。

| 種類 | 例 | どこから |
| --- | --- | --- |
| 型 | 数値列に文字、日付として読めない | DB 定義（自動） |
| 桁数 | VARCHAR(20) に 21 文字 | DB 定義（自動） |
| 必須 | NOT NULL の列が空 | DB 定義（自動） |
| 参照先 | 存在しないカテゴリコード | 外部キー（自動） |
| キー | 同じ商品コードが 2 行、DB にない | 主キー（自動） |
| 業務ルール | 価格は 0 より大きい、変動は ±50% 以内 | 設定ファイル |

## 6. バックアップとエビデンス

- 標準はファイル出力: 変更前後の Excel、戻し用 SQL、実行ログ。DB に手を入れずに使え、承認資料にそのまま添付できる。
- DB の履歴テーブルへの保存はオプション（テーブル作成の許可が要るため）。
- 戻し用 SQL は「今の値がこのツールで入れた値のままなら戻す」形にし、後から入った別の更新を上書きしない。

## 7. 似た道具

「DB 定義で検証し、差分を承認に回し、戻せる形で反映する」を一つでやる OSS は見当たらない（2026-10-17 調査）。

| 類似 | できること | 足りないもの |
| --- | --- | --- |
| SqlXl（MIT、.NET） | Excel から SQL Server へ UPDATE、DB 制約で検証 | 差分の承認資料、戻し |
| Bytebase | SQL のレビューと実行、戻し SQL 生成 | 入力は SQL。Excel 取込や値の検証はない |
| Flatfile、OneSchema（商用 SaaS） | 取込データの検証と修正の UI | DB につながらない。データが外部に出る |
| react-spreadsheet-import | 取込と検証の React 部品 | DB 定義、差分、反映、戻しがない |
| DBeaver などの DB ツール | CSV をテーブルに取込 | 開発者向け。承認資料や戻しは人手 |

## 8. 名前

**harikit**（2026-10-17 決定）。「貼り」＋ kit。DB の上に新しい値を貼り替える道具、という意味で、Excel からの取込にも通じる。npm・NuGet とも空いている。
